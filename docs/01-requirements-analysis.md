# 01 · 项目需求分析

> 所属项目：项目一 —— 企业知识库与智能业务服务平台
> 文档定位：第 1 章交付物之一，明确「为什么做」「给谁用」「做什么」「做到什么程度」。

---

## 1. 项目背景

### 1.1 企业为什么需要知识库系统？

一家中型企业拥有多个部门，知识分散在不同载体与人员手中：

| 部门 | 典型知识资产 |
| --- | --- |
| 人力资源部 | 员工手册、考勤制度、薪酬制度、入职流程 |
| 财务部 | 报销制度、发票规范、付款流程、预算制度 |
| 采购部 | 供应商准入规范、采购制度、质检标准 |
| 产品部 | 产品说明书、产品参数、产品使用手册 |
| 售后部 | 故障处理手册、售后政策、维修案例 |

这些知识以 PDF、Word、Excel、图片等形式分散保存，带来六类问题：

| 问题 | 具体表现 | 造成的影响 |
| --- | --- | --- |
| 知识分散 | 文档保存在不同部门和人员电脑中 | 查找困难 |
| 信息重复 | 相同制度存在多个版本 | 容易引用错误 |
| 人工查询 | 员工需要询问其他部门 | 沟通成本高 |
| 文档更新 | 制度更新后旧文档仍然存在 | 答案可能过时 |
| 权限复杂 | 不同部门只能访问部分资料 | 存在数据泄露风险 |
| 传统搜索能力有限 | 只能通过关键词搜索 | 很难理解自然语言问题 |

**核心诉求**：员工不再需要「先找文档、再自行阅读」，而是直接提问，系统自动检索有效制度、整理答案，并返回文档名称、章节与页码。

### 1.2 项目业务定位

本项目定位为：

> 面向企业内部知识管理和业务咨询场景，提供文档接入、知识处理、混合检索、智能问答、权限控制、版本管理和效果评估的**一体化 RAG 平台**。

第一期聚焦三个场景：

1. **企业内部知识问答**：查询制度、报销流程、审批规范、员工手册等。
2. **产品售前咨询**：查询型号、参数、功能、适用场景与产品差异。
3. **售后知识辅助**：查询故障手册、维修流程、售后政策与历史案例。

**边界**：第一期不做 ERP/CRM 集成，不纳入供应链 Agent（归项目二）。项目一只提供知识检索能力。

## 2. 用户角色与权限需求

### 2.1 角色定义

| 用户角色 | 主要职责 | 权限范围 |
| --- | --- | --- |
| 超级管理员 | 管理用户、部门、系统配置 | 全局管理 |
| 知识库管理员 | 创建知识库、上传和维护文档 | 授权知识库 |
| 普通员工 | 查询企业知识、查看答案引用 | 被授权的知识库 |
| 部门负责人 | 管理本部门知识、查看使用情况 | 本部门及授权范围 |

### 2.2 权限设计核心原则

> **用户能否访问知识，不能由大模型判断，必须由后端权限系统判断。**

具体要求：

- 财务部员工可查询财务制度；普通员工只能查询公开财务制度。
- 财务部门内部敏感文件，只能由授权用户访问。
- 即使用户通过 Prompt 要求模型读取其他部门文档，系统也不能返回未授权内容。
- **权限必须在检索阶段执行**（检索前过滤），而不是等模型生成答案后再判断。

## 3. 功能需求清单

九个功能域，按优先级划分：

| 功能模块 | 具体需求 | 优先级 |
| --- | --- | --- |
| 用户认证 | 登录、JWT、用户身份识别 | P0 |
| 知识库管理 | 创建、修改、删除、授权 | P0 |
| 文档管理 | 上传、查看、更新、删除 | P0 |
| 文档处理 | 解析、清洗、切片、向量化 | P0 |
| 检索系统 | 向量检索、关键词检索、混合检索 | P0 |
| 智能问答 | 多轮对话、答案生成、引用溯源 | P0 |
| 文档版本 | 版本记录、重新索引、失败恢复 | P1 |
| 知识图谱 | 实体关系抽取、图检索 | P2 |
| 评估监控 | RAG 评估、链路追踪、成本统计 | P1 |

**优先级说明**：
- **P0**：核心业务必须完成。
- **P1**：L3 工程交付必须补齐。注意 P1 并非可有可无 —— 文档版本、失败恢复、评估监控都必须在交付前完成。
- **P2**：增强能力。

## 4. 非功能需求清单

功能需求决定系统「能做什么」，非功能需求决定系统「能否稳定安全运行」。

| 维度 | 需求 |
| --- | --- |
| 可用性 | 模型服务异常时返回可理解的错误，不导致后端崩溃 |
| 性能 | 检索、重排、生成分别统计耗时 |
| 安全性 | 用户认证、知识库授权、检索权限过滤 |
| 可靠性 | 文档处理失败可重试，重复任务不会破坏数据 |
| 可维护性 | 模块分层、统一日志、配置与异常处理 |
| 可扩展性 | 支持新增解析器、Embedding 模型和 LLM |
| 可观测性 | 能够追踪一次问答的完整执行过程 |
| 可测试性 | 核心模块有单元测试、集成测试和端到端测试 |

### 4.1 可验证的项目目标（测试环境第一版）

不宣称未经压测的并发能力，先制定可验证目标：

- 20 个并发问答请求下服务保持稳定。
- 检索链路 P95 耗时不超过 2 秒。
- 非模型类基础 API 的 P95 耗时不超过 500 毫秒。
- 文档处理失败后可查询失败原因并重新执行。
- **未授权用户的知识检索成功率为 0**。
- 所有问答请求都能关联到请求 ID 和完整追踪记录。

> 上述数值后续需根据硬件、模型部署方式、数据量和测试结果调整；模型生成耗时不能与普通 API 耗时混为一谈。

## 5. 需求小结

| 交付项 | 结论 |
| --- | --- |
| 业务定位 | 一体化企业知识 RAG 平台，非简单 PDF 问答机器人 |
| 用户角色 | 超管 / 知识库管理员 / 普通员工 / 部门负责人 |
| 功能范围 | 9 个功能域，P0 六个 + P1 三个 + P2 一个 |
| 核心原则 | 权限后端判定、检索阶段过滤、证据不足拒答、可追溯引用 |
| 质量目标 | 一组可压测验证的量化指标，而非空头承诺 |
