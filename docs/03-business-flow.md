# 03 · 核心业务链路设计

> 所属项目：项目一 —— 企业知识库与智能业务服务平台
> 文档定位：第 1 章交付物之一，明确两条核心链路（知识构建 / 智能问答）与 L3 可靠性设计。

---

## 0. RAG 基础原理

**RAG（Retrieval-Augmented Generation，检索增强生成）** 的核心思想：先从外部知识库检索与用户问题相关的信息，再把检索结果提供给大模型，让大模型基于这些信息生成答案。

企业知识具有「私有、易变、多版本、需权限、需追溯」等特点，单纯依赖模型参数知识无法满足，因此引入 RAG 将外部知识注入推理过程。

RAG 包含两个不能混为一谈的过程：
1. **离线知识构建**：提前把企业文档处理成可检索的数据。
2. **在线问题回答**：用户提问时检索知识并生成答案。

### RAG 与 Fine-tuning 的区别

| 对比维度 | RAG | Fine-tuning |
| --- | --- | --- |
| 核心目的 | 引入外部知识 | 调整模型行为和能力 |
| 知识更新 | 更新知识库即可 | 通常需要重新训练 |
| 数据来源 | 文档、数据库、外部知识 | 训练样本 |
| 可追溯性 | 可以关联检索来源 | 不天然提供来源 |
| 适用场景 | 企业知识问答 | 格式、风格、任务行为适配 |

本项目第一期以 RAG 为核心，不需要为使用 LoRA 而强行微调模型。

## 1. 知识构建链路（离线）

```
原始文档 → 文件解析 → 文本清洗 → 文档切片(Chunking) → 生成 Embedding → 写入 Milvus
                                                              ↘ 文档/切片元数据写入 PostgreSQL
```

### 1.1 完整流程

1. 管理员上传 PDF、Word、Excel 或图片。
2. 后端校验文件格式、文件大小和用户权限。
3. 原始文件保存到文件存储。
4. PostgreSQL 创建文档记录。
5. 创建异步处理任务。
6. Celery Worker 执行文档解析。
7. 将解析结果清洗成统一数据结构。
8. 根据文档结构进行 Chunking。
9. 使用 BGE-M3 生成 Embedding。
10. 将向量写入 Milvus。
11. 将 Chunk 和文档关联信息保存到 PostgreSQL。
12. 验证索引数据后更新文档状态。

流程图见 `docs/diagrams/ingestion-flow.svg`（另附 `ingestion-flow.mmd` Mermaid 源文件）。

### 1.2 为什么必须异步处理？

文档解析、OCR 和批量 Embedding 都可能耗费较长时间，若全部放在 HTTP 请求中执行，会出现：
- 请求超时；
- Web Worker 被长时间占用；
- 大文件导致内存压力；
- 多用户同时上传时服务响应变慢。

**正确做法**：HTTP API 创建文档记录 → 提交任务 → 立即返回 `task_id` → Celery Worker 后台处理 → 用户查询任务状态。

上传接口示例返回：

```json
{
  "document_id": "doc_10001",
  "task_id": "task_20001",
  "status": "PENDING",
  "message": "文档已提交处理"
}
```

> 这只是本章设计的接口示例，后续实现时会进一步确定字段类型和统一响应结构。

## 2. 智能问答链路（在线）

```
用户问题 → 身份认证与权限识别 → 问题改写/意图识别 → 混合检索 → 候选融合
        → Reranker 重排 → 相关性判断 → 构建 Prompt → LLM 生成 → 引用溯源与答案返回
```

流程图见 `docs/diagrams/qa-flow.svg`（另附 `qa-flow.mmd` Mermaid 源文件）。

### 2.1 为什么需要多个检索阶段？

向量检索、关键词检索和重排序解决的问题不同：

| 技术 | 主要作用 | 优势 |
| --- | --- | --- |
| BM25 | 关键词匹配 | 专有名词、编号、错误码 |
| Dense Retrieval | 语义向量检索 | 自然语言语义匹配 |
| RRF | 多路检索结果融合 | 结合不同召回来源 |
| Reranker | 候选结果精排 | 提高最终相关性 |

**示例**：用户问「E102 错误代码如何处理？」—— BM25 对精确编号有价值；向量检索能找到语义相似的故障描述；Reranker 再判断哪个片段最相关。因此本项目采用混合检索架构。

### 2.2 三个关键设计

**① 权限过滤必须在检索阶段生效**

不能先检索所有文档，再让模型挑选有权限的内容。正确链路：

```
用户身份 → 后端获取授权知识库 → 构建检索过滤条件 → 只检索授权范围内的文档
```

**② 检索结果必须可追溯来源**

每个 Chunk 至少关联：`document_id`、`chunk_id`、`document_name`、`page_number`、`section_title`、`document_version`、`knowledge_base_id`，以便生成答案时返回引用来源。

**③ 证据不足时不能强行生成答案**

知识库缺乏依据时，不能编造内容，应返回：

> 当前知识库中没有检索到足够的制度依据，建议联系相关部门确认。

## 3. L3 工程设计：异常路径与可靠性

### 3.1 文档处理失败怎么办？

不能只写一个 `try-except` 就返回失败，需要设计任务状态机：

```
PENDING → PROCESSING → SUCCESS
                    ↘ FAILED → RETRYING → SUCCESS
                                      ↘ FAILED
```

每次任务至少记录：`task_id`、`document_id`、`task_type`、`status`、`retry_count`、`error_message`、`started_at`、`finished_at`。

### 3.2 PostgreSQL 与 Milvus 数据不一致怎么办？

**场景**：PostgreSQL 保存了 100 个 Chunk，Milvus 只成功写入 80 个向量，Worker 在写入过程中异常退出 —— 此时不能把文档标记为成功。

**需要设计**：处理任务状态、Chunk 索引状态、批次写入记录、重试机制、失败补偿、索引完整性校验。

**方案**（无需一开始引入分布式事务，用任务状态管理 + 补偿机制即可支撑本项目规模）：

```
创建文档处理任务 → 解析并生成 Chunk → 保存 Chunk 元数据 → 批量写入 Milvus → 检查写入结果
                                              ├─ 全部成功 ─→ 文档 READY
                                              └─ 部分失败 ─→ 记录失败项 → 重试 / 补偿
```

### 3.3 用户权限如何保证？

不能只在前端隐藏按钮，也不能只靠 Prompt 约束模型。正确链路：

```
用户请求 → JWT 验证 → 获取服务端用户身份 → 查询知识库授权
        → 生成检索过滤条件 → Milvus/BM25 检索 → 仅返回授权范围内的 Chunk
```

**必须配套自动化测试**：
- 用户 A 能否读取授权知识库？
- 用户 A 能否读取未授权知识库？
- 用户 A 能否通过修改请求参数越权？
- 用户 A 能否通过多轮对话间接获取其他部门知识？
- 删除授权后，旧会话是否仍能检索到受限内容？

### 3.4 模型服务不可用怎么办？

模型服务可能出现：连接超时、请求超时、HTTP 429、HTTP 500、输出格式错误、Token 超限。

需对模型调用统一封装，实现：请求超时、有限重试、指数退避、错误分类、并发限制、模型调用日志、友好错误提示。

> 不要在每个业务模块里单独写一套模型调用逻辑。

## 4. 链路小结

| 链路 | 触发时机 | 关键机制 |
| --- | --- | --- |
| 知识构建 | 管理员上传文档 | 异步任务、状态机、重试、索引一致性校验 |
| 智能问答 | 用户提问 | 检索阶段权限过滤、混合检索、相关性判断、拒答 |
| 可靠性 | 全链路 | 幂等、补偿、统一模型封装、友好错误提示 |
